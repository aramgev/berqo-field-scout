# Implementation choices

The challenge PDF and ChatGPT spec were treated as source material describing the desired product. The user's direct request controls scope: a separate public app, React Native, apricot, photo upload, fast implementation and future integration into private Berqo. No private application was imported.

Expo SDK 57 / React Native 0.86 with Expo Router (required by the generated project instructions) provides native image picking, image conversion, sandboxed persistence and cloud APK builds. ONNX Runtime 1.24.3 provides asynchronous native inference. The tiny `jpeg-js` and `base64-js` packages turn a bounded 224×224 JPEG into normalized RGB tensors. Preprocessing work remains small; larger evidence photos are resized natively to at most 1600 pixels.

The feature core is dependency-free TypeScript. UI uses only React Native components/system fonts, so no image assets or design framework need to be moved into Berqo. The existing generated app icon is a placeholder; it is not a private Berqo brand asset.

Storage uses one JSON file per passport and persistent JPEG copies, weather/preferences JSON and staged writes, behind interfaces. No heavyweight database, authentication or production service is required. Uninstalling/clearing application data deletes these records. Future Berqo can replace the repository with its own store and migrations.

Model training uses MobileNetV3 Small and a real apricot-specific dataset. Class order/preprocessing/confidence/versions live in crop-pack metadata. A bundle script makes a trained pack part of the APK; an importer allows a completed model to be added to a previously built APK. Missing model is explicit and never falls back to fake disease predictions. Float32 export is a deliberate first-run reliability choice; quantization can follow measured accuracy and device tests.

Safe advice is short, structured, local and separate from model output. Labels without condition-specific source links use general observation/expert-review guidance. No chemical treatment or dosing is supplied. Scores are called model scores rather than calibrated clinical/agronomic probability. Low confidence, small class margin, unsupported labels and invalid scores lead to uncertainty; a high score can still be wrong.

Weather uses Open-Meteo's non-commercial public API with a foreground phone-location adapter (`LocationProvider`). The user requests a fresh high-accuracy fix; permission denial, disabled services and a 25-second timeout have actionable messages. Saved coordinates include source, timestamp and reported accuracy. Manual coordinates remain available. Moving to a different location invalidates its old forecast. Coordinates are sent to Open-Meteo only for forecast requests; photos stay local. Three daily min/max/precipitation forecasts use the orchard timezone and hourly UTC instants. The next 48 hours drive frost/rain inspection reminders and a dry-period soil-moisture check, backed by UC IPM sources. No irrigation volume, heat-damage threshold or fungal diagnosis is inferred. Forecasts cache locally; after 24 hours suggestions are suppressed. Sample weather is explicitly marked and never overwrites the real forecast cache.

Sync uses an isolated local demonstration adapter. It requires connectivity so store-and-forward can be demonstrated, simulates failures, records a local receipt and never falsely marks an expert request delivered. Real delivery can be supplied through `SyncAdapter` without changing the domain engine. JSON/photo sharing is user initiated.

Deferred: production backend, automated background sync, agronomist portal, push alerts, speech/TTS, extra crops, crop-pack marketplace, cloud image diagnosis, paid AI APIs, local LLM, satellites/drones and private Berqo logic.

Training/evaluation, signed APK creation and physical-device inference are distinct readiness gates. Typechecking, tests, Metro export and generated Android configuration cannot substitute for actual phone evidence.

Android build compatibility: ONNX RN 1.24.3's Gradle script references `VersionNumber`, removed by the current Gradle toolchain. `plugins/withOnnxGradleCompat.js` replaces that comparison with the already-defined React Native minor-version integer during prebuild and pins the Android AAR to matching stable 1.24.3 instead of the upstream dynamic nightly dependency. It is idempotent and fails visibly if upstream changes the expected code. No generated application native files are maintained by hand. Upstream context: https://github.com/microsoft/onnxruntime/discussions/32604 and https://github.com/microsoft/onnxruntime/issues/32744.

The plugin also explicitly links the ONNX bridge with Android's 16 KB page-size flags because React Native's NDK r27 does not apply them automatically to this separate CMake target. The preview profile sets `BERQO_ANDROID_ABIS=arm64-v8a` for modern Android phones and faster, smaller demo builds. Production keeps default architectures. Other ABI selections can be supplied through that environment variable.

Native registration: ORT's obsolete `unimodule.json` causes Expo to omit its Java ReactPackage even though Gradle compiles it. Root `react-native.config.js` supplies the explicit Android package import/instance. The actual Expo autolinking output was checked before (absent) and after (registered). The classifier checks native registration before evaluating ORT's import-time JSI binding, so Expo Go or incomplete native builds fail safely rather than crashing. Upstream context: https://github.com/microsoft/onnxruntime/issues/29004. Keep this root configuration when carrying the ONNX adapter into another Expo app.
